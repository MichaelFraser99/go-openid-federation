# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

A Go library implementing the [OpenID Federation](https://openid.net/specs/openid-federation-1_1.html) specification. It provides the building blocks for participating in a federation as either a **server** (an entity/intermediate/trust anchor that publishes statements and serves federation endpoints) or a **client** (a relying party that builds and resolves trust chains). This is a library, not a runnable service — the `Makefile` `build` target that produces an AWS Lambda `bootstrap`/`main.zip` refers to a `main.go` that does not exist in this repo; treat it as a downstream-consumer packaging convention, not something you can run here.

## Commands

- **Test:** `go test ./...` (also `make test`). CI runs `go test -v ./...` **and then a second `go test -race ./...` pass**, so a change must be clean under the race detector as well. The race pass is the one that catches a wall-clock assertion written with too little headroom: a GitHub runner is two cores, so a budget that holds here can fail there.
- **Single test:** `go test ./model -run TestMetadataProcessingE2E` (add `-v` for verbose).
- **Lint:** `golangci-lint run` (version pinned to v2.13.1 in CI and pre-commit; match it locally). Run `pre-commit run --all-files` to reproduce the full pre-commit gate (end-of-file/trailing-whitespace fixers, yaml check, `no-commit-to-branch`, and `golangci-lint-full`).
- **Go version:** 1.26 (see `go.mod`).

## Architecture

Four packages, layered:

- **`model/`** — All exported types, JWT/entity-statement data structures, and the metadata-policy engine. This is the bulk of the code and where most logic lives. Depends on nothing else in the repo.
- **`internal/`** — The federation protocol mechanics, split by concern: `entity_configuration` (fetch/verify an entity's own `.well-known/openid-federation`), `subordinate_statement` (fetch a statement about a subordinate from its superior's fetch endpoint), `entity_statement` (low-level JWT parsing), `trust_chain` (chain building + metadata resolution), `trust_marks`. These consume `model` and perform the actual HTTP + signature verification.
- **`server/`** — HTTP handlers for the federation endpoints, wired up in `server/server.go`. `Server.Configure(*http.ServeMux)` registers routes conditionally based on config (see below).
- **`client/`** — Thin public wrapper exposing `BuildTrustChain` and `ResolveMetadata`, delegating to `internal/trust_chain`.

### Cryptography

All JWS/JWK/JWT signing and verification goes through the sibling library `github.com/MichaelFraser99/go-jose` (`jwa`, `jwk`, `jws`, `jwt`, `model` subpackages, where `jwa` holds the algorithm identifiers). Do not hand-roll crypto — entity statements and trust marks are signed JWTs handled via that dependency.

### Anchoring the top of a chain

Two functions, and the split matters. `verifyTrustAnchorRequested` judges the caller's argument and this deployment's own configuration — nothing from the chain — and runs at the entry of `BuildTrustChain` and `ResolveMetadata`, before any network request, because an unauthenticated caller must not be able to spend a full federation walk on an anchor this deployment was never going to accept. `verifyTrustAnchor` judges the statement at the top of the chain and runs where that statement is first available: once in `BuildTrustChain` after `verifyChainLinks`, and once in each of `ResolveMetadata`'s two branches for the last entry. All three invocation points have their own test, because mutation showed that deleting two of them left the suite green. It is not the only place a chain's anchor is judged — the omitted-anchor branch compares the chain's own issuer to the named anchor inline, before fetching it, so a caller-supplied chain cannot direct an outbound request at an entity the caller did not name.

`verifyTrustAnchor` checks the identifier, then the signature, and **only the second has cryptographic content**. The identifier check requires `iss` and `sub` both to equal the named anchor, which is what makes the last entry an entity configuration rather than a statement about someone else; checking `iss` alone leaves `Sub` unpinned, which a mutant exploits. The signature check applies only when `Configuration.TrustAnchors` holds keys for that anchor, which §4 puts out of band and the library therefore cannot obtain itself.

So with `TrustAnchors` unset, a chain whose last statement is the attacker's own self-signed entity configuration labelled with the anchor's identifier **is accepted**. That is the documented default and `TestResolveMetadata_AForgedAnchorIsRefusedOnlyWhenKeysAreHeldForIt` pins both halves of it — the forgery resolving with no keys held, and being refused with them. Any README or commit text claiming #48's attack is closed in the default configuration is wrong.

`TrustAnchorsConfigured` tests `TrustAnchors != nil`, not its length, so a non-nil map with no entries refuses every anchor rather than falling back to the no-check mode. An anchor list that parsed to nothing is a configuration fault. `TrustAnchorKeys` returns `configured = false` for an anchor absent from the map or mapped to an empty set.

**"Usable" must mean what go-jose means, not what the JWK syntax allows.** `entity_statement.UsableVerificationKeys` counts a key only if `jwk.PublicFromJwk` builds it *and* `jws.GetValidator` returns a validator for some algorithm; `jws/validate.go` names `EdDSA` only to refuse it, so there is no validator for it. An earlier version of this code filtered on `model.ValidateJWKShape`, which asks only for a non-empty `kty`, so an operator pinning an Ed25519 anchor key — valid JOSE, and the default in several ecosystems — passed the filter, failed verification, and was told 404 that *the anchor's* configuration was unsigned: their own misconfiguration reported as the peer's fault, on every request. One definition now serves both the entry check and the chain check, so a set with no usable key answers `server_error` before any walk. Watch for this shape of mistake generally — a local predicate weaker than the library's, with the gap surfacing as a peer-blaming error.

`model.ValidateJWKShape` is still load-bearing inside that predicate rather than tidy: go-jose asserts `kty.(string)` unchecked, so a configured key whose `kty` is an object or a number panics without it. `TestVerifyAgainstAnyKey` holds those two cases and a `recover` that fails the test.

`entity_statement.VerifyAgainstAnyKey` is what the configured set goes through, **not** `VerifyAgainstJwks`. Selection by `kid` is wrong here: §10.2 asks only for "a public key of the Trust Anchor", RFC 7517 §4.5 keeps `kid` optional, and an operator holding the anchor's key under a label of their own, or pasting its published JWK Set verbatim, would otherwise have every resolve against that anchor refused with a message blaming the anchor. It does not consult `use` or `key_ops`, which is #188.

**A chain of one entry is not a Trust Chain, and both public entry points refuse to produce one.** §4 says a Trust Chain "includes the Subordinate Statement issued by the Trust Anchor about ... the Trust Chain subject" and that only the anchor's *Entity Configuration* MAY be omitted from the array, so the minimum is two entries. §10.2's own step list does not catch this — with `i == 0` both of its `j = 0,...,i-1` loops are empty and every remaining step passes on a self-signed configuration, which is why an implementation written from the step list alone accepts it. §10.2's preamble is what makes §4 binding: "it MUST now verify that it is a proper Trust Chain using the rules laid out in that section". `Client.ResolveMetadata` and `/resolve` both refuse `subject == trustAnchor` with `invalid_request`, which is the only way a one-entry chain could satisfy the identifier check. §4.1 still allows resolving a Trust Anchor against a *higher* anchor, so nothing legitimate is refused.

`ResolveMetadata`'s single-entry path therefore survives for internal callers and tests only. Do not remove the `subject == trustAnchor` guards on the assumption that path is dead: they are what keeps it unreachable.

Every call site reachable from a public entry point passes the anchor the *caller* named, never the issuer of the chain's own last statement, which is the bypass this guards against. A test fixture for a one-entry chain names the subject as the anchor, because that chain's last statement is the subject's own entity configuration. The exception is `internal/trust_marks`, which walks to `trustAnchorConfiguration.Sub`, taken from the chain's own last statement; that is safe only transitively, because `verifyTrustAnchor`'s `Sub` check has already pinned that value to the caller's anchor. The `Sub` half of the identifier check is what holds it together, not the call site.

Refusals here log at Info, matching every other refusal in the walk, with two exceptions, both at Error because both mean an operator must act: a configured key set holding no key that can verify a signature, and a chain ending in a configured anchor unsigned by any key held for it — either a key rotation this deployment has not picked up, or a forgery.

Nothing on this path may answer a 5xx for peer-chosen input. Three places got that wrong and are fixed: a subject named as its own trust anchor (now `invalid_request`), a configured key set with no usable key (now caught at entry, so the 5xx is never reachable after a walk), and an anchor whose entity configuration cannot be fetched, which returned the transport error unwrapped and so echoed the peer's HTTP status into a 500 body — a probe oracle. `TestResolveMetadata_AnUnreachableAnchorIsNotAServerFault` walks six peer statuses and asserts none reaches the description.

### Constraints (§6.2)

`EntityStatement.Constraints` is typed and parsed in `UnmarshalJSON` (§3.2 step 19), so a malformed claim refuses the statement. `verifyChainConstraints` runs in **both** `BuildTrustChain` (after `verifyChainLinks`) and `ResolveMetadata` (after the subject key check), because a caller can hand `ResolveMetadata` a chain `BuildTrustChain` never saw. It works on the parsed chain in subject-first order: for the subordinate statement at index k, `max_path_length` counts k − 1 intermediates, and `naming_constraints` covers `Sub` of entries 0..k, which is the subject and every entity below the setter but not the setter itself. Each statement is judged independently; do not combine constraints across levels.

Host matching has two deliberate refusals. A non-ASCII host is refused under any naming constraint unless `Configuration.HostToASCII` is set, because Go's HTTP client connects to its punycode form and a string comparison would let the Unicode spelling past an exclusion. Matching it needs IDNA, which is deliberately not a dependency: the consumer opts in with `idna.Lookup.ToASCII`, the profile `net/http` uses. The converter is called only for a non-ASCII host, and its output goes through `NormaliseConstraintHost` again, so an error or a non-ASCII result still refuses. A host is lower-cased and stripped of one trailing dot, and must then be a well-formed domain name (`validDomainName`: letters, digits and inner hyphens, labels of 1 to 63 octets, at most 253 octets, a last label that is not all digits). RFC 5280 says an application MUST reject a URI whose host is an IP address when a URI constraint applies, and §6.2.2 incorporates that, so an IP host is refused under any naming constraint, not judged against it. The first version of this change accepted an IP host under an exclusion and pinned that in its tests, which let an entity at `https://203.0.113.5` escape every exclusion; the rule also catches `leaf.example.com..`, whose leftover dot made `HasSuffix` miss. Constraint names go through the same `validDomainName`, which is what stops a numeric constraint such as `192.0.2.1` matching an address. Two rows guard the normalisation and pass only with it: a trailing-dot host *permitted* as itself, and a 63-octet label. A row that expects only refusals cannot tell normalising from rejecting.

`allowed_entity_types` is applied in `ResolveMetadata` only, between `ApplySuperiorMetadata` and `ProcessAndExtractPolicy`, which is the order §6.2.3 names; `ApplyPolicy` iterates only the types the subject still has, so a policy cannot bring a removed type back. A nil `AllowedEntityTypes` is an absent member and an empty one is `[]`; `Constraints.MarshalJSON` keeps that distinction, and so does `NamingConstraints.Permitted`. An empty `permitted` is refused at parse, because every chain has at least one entity below the setter, so it could only ever refuse the chain, and refusing it there names the real fault; `Permits` still treats a Go-built empty list as permitting nothing. An empty `excluded` is accepted, since refusing it would change an outcome, not just a message.

### The server's own identifier as a `sub` (#208, #209)

`model.NamesTheSameEntity` is the self-statement guard, used only by the `/fetch` handler and `subordinate_statement.New`. It compares in a canonical form that refuses more than §16 calls equal, on purpose: host case, trailing dot, default port, unreserved percent-encodings, slash and dot segments, and **path case**. Path case is not an RFC 3986 equivalence; it is folded because a store whose collation is case insensitive resolves `/TA` onto the server's own `/ta` row, and the server would then sign a statement vouching for its own keys. The cost is refusing a genuine subordinate that differs from the server only in path case.

Do not replace this with a check on keys. An earlier version of #209 refused a record holding one of the server's own federation keys, and review rejected it: §3.1 does not require a subordinate's keys to differ from its issuer's, one operator can legitimately run several entities under one HSM key, and refusing the statement does not take signing ability away from whoever holds the key. A spec-silent heuristic must not break a valid topology by default.

### Server configuration drives behavior

`model.ServerConfiguration` (in `model/model.go`) is the central config object. Capabilities are turned on by *presence of config*, not flags:

- `IntermediateConfiguration != nil` → registers `/list`, `/fetch`, `/resolve` (this entity acts as an intermediate/authority).
- `Extensions.ExtendedListing.Enabled` / `Extensions.SubordinateStatus.Enabled` → registers `/extended-list` / `/subordinate-status`.
- `TrustMarkRetriever != nil` → registers the `/trust-mark*` endpoints.

Data access is abstracted behind interfaces so consumers plug in their own storage: `Retriever` (subordinates + their signers), `TrustMarkRetriever`, `TrustMarkIssuerRetriever`, `ExtendedListingRetriever`, `SubordinateStatusRetriever`. Subordinate lookups are cached in-memory (`IntermediateConfiguration.subordinates`, TTL `SubordinateCacheTime`, `FlushCache()` to clear). `SetEntityIdentifier` / `SetHttpClient` on `Server` exist for test-server scenarios and are documented as not-for-production.

Trust chain walking is bounded three ways, all non-zero by default: `MaxTrustChainDepth` (entities on one path), `MaxEntitiesTraversed` (entity configurations fetched for one request, charged in `entity_configuration.Retrieve` on a cache miss) and their product (entities stepped into for one request, charged in `chainUpOne`). Reaching one produces `model.NewLimitReachedError`, which is `ErrInvalidTrustAnchor` and `ErrLimitReached` — never `ErrServerError` or `ErrTemporarilyUnavailable`, because the graph is the caller's choice and a bound is neither a fault nor temporary.

Two further bounds apply to one statement rather than one request. `model.VerifyJSONValueCount` runs on the raw header and body of every peer statement, trust mark and delegation **before** `json.Unmarshal` and before the signature check, at `StatementValuesLimit()`. Verifying first is no defence: an entity configuration is signed with a key from its own `jwks`, so an attacker signs their own padding, and `json.Unmarshal` materialises the whole value tree before anything can look at it. The trust marks a statement carries are base64 strings to that count, one value each, so `model.VerifyTrustMarkValueCount` charges the header and body of every mark, **and of every mark's `delegation`**, to one shared budget of the same size. Each of those three was missed by an earlier draft: per-mark caps let many marks each just under the limit add up, counting bodies alone left the headers that `FilterByTrusted` decodes before any signature, and leaving delegations out let ten 20,000-value delegations through one statement. A malformed entry must `continue`, never end the count, or one bad mark switches the budget off for the marks after it.

A chain handed to `ResolveMetadata` is the caller's, not fetched, so nothing upstream counted it. `ResolveMetadata` counts every entry with `model.VerifyTokenValueCount` before `ExtractDetails` decodes anything, and holds the chain to the depth a walk is held to: `TrustChainDepthLimit()+1` entries when the last entry is the anchor's own entity configuration, `TrustChainDepthLimit()` when the caller omitted it, because that branch appends the anchor's configuration itself. For k entities `BuildTrustChain` emits the subject's entity configuration, k-1 subordinate statements and the anchor's entity configuration, which is k+1 entries. `suppliedChainEntriesLimit` saturates at `math.MaxInt`, as `visitLimit` does: without that, `MaxTrustChainDepth: math.MaxInt` wrapped the `+1` and refused every chain. `TestResolveMetadata_ASuppliedChainIsHeldToTheDepthAWalkIsHeldTo` pins all three.

`AuthorityHintsLimit()` (§18.1: "a limit on the number of authority_hints they are willing to inspect") is applied in `chainUpOne`, after the `Iss == target` return, which is where hints are inspected. It is **not** applied when a configuration is decoded: the anchor reached as the walk's target, the anchor configuration `ResolveMetadata` fetches, and any configuration whose hints are never followed may list as many as they like. An earlier draft put it in `entity_configuration.validate` and so made an anchor with 65 superiors unreachable. A configuration over the cap is recorded as an untainted dead end. For a superior the walk tries the next hint; for the subject the walk's own `invalid_trust_chain` names the bound. Per-statement bounds are never `ErrLimitReached`, which would abort the whole walk. A value bound hit while fetching surfaces as the walk's generic "failed validation", with the bound named in the Info log, like the response-size bound. On a chain the caller supplied to `ResolveMetadata`, the 400 description names the bound and the entry index, which is safe because it describes the caller's own input.

There are two memos, and the distinction is the subtle part. `internal/resolvecache` holds the per-request one, keyed by subject and target, and a verdict reaches it only when `tainted` is false. `walkMemo` is per walk, keyed by subject, target and the depth still available, and holds every verdict together with its taint. A tainted verdict is sound to reuse inside the walk that produced it — a superior that could reach the anchor would have reached it before the walk gave up — but not across walks, which may arrive by a path where the obstacle is absent. Without the per-walk memo a graph of mutually hinting entities re-walks every simple path; `internal/trust_chain/walk_differential_test.go` checks both memos against ground-truth reachability on random graphs, including several walks sharing one cache.

### Metadata policy engine (the most intricate part)

The heart of the library is applying OpenID Federation **metadata policies** down a trust chain. Key pieces:

- **`MetadataPolicyOperator` interface** (`model/model.go`): each policy operator implements `Resolve` (apply to a metadata value), `Merge` (combine two operators of the same kind when policies from different chain levels stack), `ResolutionHierarchy` (defines the fixed order operators are applied within a claim), `CheckForConflict`, `ToSlice`, and `OperatorValue`.
- **Operators**, one file + `_test.go` each: `add.go`, `default.go`, `value.go`, `essential.go`, `one_of.go`, `subset_of.go`, `superset_of.go`. Registered/dispatched by key in `policy_operators.go`.
- **`model/helpers.go`** orchestrates: `MergePolicyOperators` (combine two policy sets for a claim, respecting `ResolutionHierarchy`), `ApplyPolicy` (apply a resolved `MetadataPolicy` to an `EntityStatement`).
- **`internal/trust_chain/trust_chain.go`** is the entry point: `BuildTrustChain` walks from leaf up to trust anchor; `ResolveMetadata` has three return paths and verifies the resolved metadata on all of them. Both pass the top of the chain through `verifyTrustAnchor`, which is the only place a chain's anchor is judged: once in `BuildTrustChain` after the links are verified, and once in each of the two branches `ResolveMetadata` has for the last entry. The multi-entry paths first apply the immediate superior's `metadata` claim, then the accumulated policy where the chain carries one; the single-entry path has neither a superior nor a policy. `CalculateChainExpiration` bounds validity to the earliest-expiring statement.

Operand comparison has two paths, and the second has a proof obligation. A value of a JSON shape is keyed by its canonical JSON (`canonicalOperandKey`); anything else, such as an infinity, invalid UTF-8 or a Go type a decode never produces, falls back to `reflect.DeepEqual`. The fallback is bucketed by `operandHash` so it stays linear (#173), and **the hash need not be injective, but equal values must hash equally**. Anything `DeepEqual` treats as equal must therefore mix identically: `-0` and `+0` (through `operandFloatBits`), map entries summed so iteration order cannot matter, an interface hashed as the value it holds. A hash that splits two equal values silently keeps a duplicate. `TestOperandHash_EqualValuesHashEqually` holds the cases, and each row asserts the fixture is equal first, so a row cannot pass vacuously.

All three walks (`normalise`, `canMatch`, `hash`) share `operandWalk`, a budget of 100,000 nodes per walk, and must count the same nodes; an interface wrapper is not a node, because `normalise` never sees one. A walk past the budget gives up: unkeyed, unmatchable, and hash 0. That one rule ends a self-referencing value, which used to overflow the stack fatally, and a value sharing a member at each level, which `canMatch`'s former depth limit of 100 still walked 2^100 times. Two `DeepEqual` values always have the same node count, so they exceed the budget together and the hash obligation holds. No JSON value comes near the budget, because a decoded statement holds at most `MaxStatementValues` values.

When adding or changing an operator, keep the three concerns aligned: resolution semantics, merge semantics across chain levels, and `ResolutionHierarchy` ordering. `model/metadata_processing_e2e_test.go` checks policy merging and application against the specification's worked examples. It does not cover the superior's `metadata` claim or resolved-metadata verification; `internal/trust_chain/chain_metadata_test.go` covers the pipeline end to end.

### Metadata entity types

Each federation entity type has its own file implementing `EntityTypeIdentifier` (a `VerifyMetadata() error` validator): `federation_metadata.go`, `openid_relying_party_metadata.go`, `openid_provider_metadata.go`, `oauth_authorization_server_metadata.go`, `oauth_client_metadata.go`, `oauth_resource_metadata.go`, `openid_wallet_provider_metadata.go`, `openid_credential_issuer_metadata.go`, `openid_credential_verifier_metadata.go`. The `Metadata` and `MetadataPolicy` structs in `model/model.go` have one field per type. Adding a new entity type touches nine places, each of which fails silently rather than at compile time, because `EntityTypeIdentifier` only requires `VerifyMetadata`: a new file with the struct, `VerifyMetadata` for claim shape and `VerifyResolvedMetadata` for required claims, an `_ EntityTypeIdentifier = X{}` assertion, the identifier in `builtInEntityTypes`, fields on both `Metadata` and `MetadataPolicy`, a case in each of `Metadata.setEntityType`/`byEntityType` and `MetadataPolicy.setEntityType`/`byEntityType`, a block in each of the four hand-written `UnmarshalJSON`/`MarshalJSON` methods, and `verify`/`verifyResolved` entries in `builtInEntityTypeDefinitions`. A new type's body must be `map[string]any`, because `ReMarshalJsonAsEntityMetadata` decodes into it and a struct body would reintroduce the member-name folding described under JSON handling. Leaving the type out of `builtInEntityTypes` routes it into `Extensions` at parse time; leaving out the `setEntityType` case routes it there during resolution, so the typed field a consumer reads stays nil. The tests that guard this are the per-type loops over `builtInEntityTypes` in `model/entity_type_test.go` and `model/chain_policy_test.go`, so adding the identifier there is what makes the rest fail loudly.

### JSON handling

`EntityStatement`, `Metadata`, and `PolicyOperators` have hand-written `UnmarshalJSON` methods that reject malformed/expired statements at parse time. `EntityStatement` validates its own required claims there; `Metadata` validates claim shape only, because a statement's metadata may be completed by a superior, so the required claims of an entity type are judged at the end of resolution instead. When touching these types, preserve the custom (un)marshalling — the JSON shape is spec-defined and validated on the way in.

Spec-defined member names must be read by their exact name. Go's `encoding/json` matches struct fields with Unicode simple folding, so a struct decode reads `keyſ` or `TRUST_MARK` as `keys` or `trust_mark`, which a conforming parser would not: anywhere a raw map check and a struct decode run over the same object, the two can disagree about what the statement says. `model.ParseJWKSet` is the one way to read a key set: it takes the keys from the exact `keys` member and leaves out an entry that is not a usable JWK, which is what RFC 7517 §5 asks, with `model.ValidateJWKShape` as the per-key check it shares with `entity_statement.SelectKey`. `model.ParseFederationEntityKeys` wraps it for the `jwks` **claim** and adds §3.1.1's rule that every key in that set carry a unique, non-empty, string `kid` — refusing the set, because that rule is a Federation MUST about the whole set and would otherwise be escaped by any entry the lenient parse leaves out. Everything else uses the lenient parse: §3.1.1 states that rule inside the definition of the `jwks` claim, and nowhere else, so a metadata `jwks` and a `trust_mark_owners` entry keep RFC 7517 §4.5's optional `kid`. Refusing a whole Entity Configuration over a `trust_mark_owners` entry would also contradict §3.1.1's instruction to ignore that claim on an Entity that is not a Trust Anchor. `model.VerifyJWKSetClaims` is the matching check for the `jwks`, `jwks_uri` and `signed_jwks_uri` metadata parameters, which §5.2.1 defines as OPTIONAL for every Entity Type except `federation_entity`, where they must not appear at all.

Keys the library publishes are held to more than keys it reads. `entity_configuration.New` refuses to publish a key of the operator's own that is not a usable JWK; `subordinate_statement.New` does not, because that set is a registrant's keys relayed by its authority, and one bad registered key must not take down the statement or anything resolved through it.

**Where the key rules bite for a configured trust anchor key.** `entity_statement.KeyCanVerify` carries `use` and the modulus rule as well as the shape and validator checks, so an anchor key the deployment configured with `use: "enc"`, or below its algorithm's minimum modulus, is refused as `server_error` at the entry of the request rather than after a walk. `VerifyAgainstAnyKey` then calls `VerifySelectedKey` per candidate, which repeats `use` and the modulus check — those two halves are **redundant** there, because every key reaching that line has already passed `KeyCanVerify`, and a mutant swapping it for `VerifyKeyAlgorithm` survives. `VerifySelectedKey` is kept because the algorithm half is not redundant and bundling the three is the right abstraction; `KeyCanVerify` is where the other two actually decide anything. Do not read the `VerifySelectedKey` call as the thing enforcing them.

Issuance must never write back into what it was given. `subordinate_statement.New` filtered the registrant's key set and assigned the result to `subjectSubordinateConfiguration.JWKs`, which is the pointer the subordinate cache hands to every caller, so concurrent `/fetch` calls for one cached subject raced under `-race` and the drop was logged once per cache period rather than once per request. Build the statement from a local set.

**One subordinate's data must never take down a response that serves others.** This rule has now been broken three times in the same place, each time by a check added for a good reason: `subordinate_statement.New` refusing a whole statement over one registrant's key, `entity_configuration.New` failing over one subordinate's weak signer, and `/extended-list` answering 500 for the whole listing when one entry could not be scanned. The shape to watch for is a `return` inside a per-entry loop. On `/extended-list` every per-entry failure — unserialisable, unreadable once serialised, or nested deeper than the key scan reaches — omits that entry and logs it, so the listing stays up for everyone else. Fail closed for the entry, not for the endpoint.

Private key material is the rule, but **the granularity differs by whose key it is, and that distinction is the whole design**. `model.VerifyPublishableJWK` refuses a key carrying any member from RFC 7518 section 6's private set (`d`, `p`, `q`, `dp`, `dq`, `qi`, `oth`, `k`) or the AKP type's `priv`. For the operator's **own** keys — the `jwks` claim, every entity type's metadata `jwks`, and `trust_mark_owners` — `entity_configuration.New` refuses the whole statement, because the operator is the only party who can fix it and publishing is the harm. For a **registrant's** keys, `subordinate_statement.New` drops the offending key and logs at error level: refusing the statement would let one registrant's mistake 500 its authority's `/fetch` and, worse, the whole `/extended-list` response for every other subordinate. A subject whose every registered key is unpublishable is refused alone, with `invalid_subject`. A per-subordinate signer key below its algorithm's minimum modulus is likewise left out of the published set rather than failing the authority's own entity configuration, which would take the authority and its entire subtree offline. The first version of this change got all three of these wrong and contradicted the rule stated in the paragraph above it.

**The refusal scans the statement after it is serialised, not the Go values that built it.** `model.VerifyPublishableStatementKeys` runs over the `map[string]any` that `New` is about to sign, finds every `jwks` member at any depth, and checks every `keys` entry under it. Two earlier versions were both wrong, and in the same way: one used `ParseJWKSet`, the lenient reader, so a private key with no `kty` was dropped before the check saw it; the next walked the typed `Metadata`, so it recognised `map[string]any{"keys": []any{...}}` and missed `josemodel.Jwks` — the library's own key set type, and what any Go consumer would naturally write. Scanning what is actually serialised is the only form that cannot be escaped by a shape, and it catches `metadata_policy` operands for free, which the typed walk did not reach at all.

The error names the path it found (`metadata.openid_relying_party.jwks`), because an operator with nine entity types needs to know which one.

`/extended-list` is the other publication path and does not go through `New` for the retriever's own claims, so `model.StripUnpublishableKeys` drops offending keys from each entry there — drop rather than refuse, because those are registrant claims.

The read path only logs, and **when** it logs is part of the design. `model.LogPrivateKeyMembers` records one line per key set, naming the issuer, the subject and at most `maxLoggedPrivateKeys` key IDs, and it runs only once **every** identity check on the statement has passed — not merely after the signature. A self-signature proves nothing about the entity whose URL was fetched, and any superior reached during a walk can answer with another entity's `sub`, so logging earlier lets anyone make the library accuse an innocent peer of leaking its key. That is why the subordinate statement log lives in `Retrieve`, after the `sub` check, rather than in `Validate`, which does not know which subject was asked for. Both halves of that matter: logging before verification lets anyone who can answer one `.well-known` fetch make the library accuse an innocent peer, and a line per key let one 800 KB statement produce 28,000 error records, times `MaxEntitiesTraversed` fetches per request. Verification continues regardless, because a peer that published its own private key has already leaked it and refusing would deny service over the peer's mistake.

`model.VerifyKeyStrength` holds an RSA key to RFC 7518 sections 3.3 and 3.5's "2048 bits or larger" — a MUST **for the RS and PS algorithms specifically**, not a general strength policy. Do not extend it to a strength threshold the specifications do not state: there is no EC curve rule and no OKP rule here on purpose. `MaximumRSAKeyBits` (8192) is the one ceiling, and it is a denial-of-service bound, not a strength rule: RFC 7518 sets no maximum, but the RSA public operation grows quadratically with the modulus, and an entity configuration is verified against keys it chose itself, so a 1-megabit key in a 408 KB statement cost 7.6 s per verification (#214). 8192 is Go's own `crypto/tls` default. The error says it is this library's limit and cites no RFC. Because `VerifySelectedKey` and `KeyCanVerify` both call `VerifyKeyStrength`, the ceiling reaches every read path before go-jose uses the key. Issuance is weaker, and do not claim otherwise: `entity_configuration.New` and `subordinate_statement.New` apply both bounds only to a key that declares a string `alg` (#192), and `/extended-list` relays keys through `StripUnpublishableKeys`, which applies neither, so the server can still publish a key its own read path refuses. Five things keep it from judging a key it has no business judging — a `kty` that is not `RSA`, an algorithm outside those two families, an absent or non-string modulus, an empty modulus, and one it cannot base64url-decode all return nil. `big.Int.SetBytes` is what computes the size, so leading zero octets do not inflate it; a byte count would, and `model/key_material_test.go` pins the 2047/2048 boundary and a padded modulus to keep the two distinguishable.

### Trust mark delegation

§7.3 step 8 makes a `delegation` claim mandatory whenever the trust mark's type appears in the trust anchor's `trust_mark_owners`, and step 9 sends a delegation that is present through §7.2.2's nine steps. `verifyDelegationRequirement` runs the two §7.3 steps and `verifyDelegation` runs the nine. A delegation whose type has no `trust_mark_owners` entry is **refused**, not ignored: §7.2.2 step 9 takes the verifying keys from that claim, so with no entry the validation cannot succeed.

Two clauses are easy to get backwards. `exp` is OPTIONAL and §7.2.1 says its absence means the delegation does not expire, so an absent `exp` must not fail. `iat` is REQUIRED, so an absent `iat` must fail rather than being read as always-valid.

**Three checks are redundant for the verdict and kept for the description** — §7.2.2 steps 3, 6 and 7, where 6 means only the *future-`iat`* comparison. go-jose's `jwt.Validate` rejects a future `iat` and a past `exp` while checking the signature, and refuses `none` or an absent `alg` through its own header validation. Removing any of the three leaves the verdict unchanged but makes the refusal name the wrong fault — an expired delegation reported as `the delegation signature does not verify against the owner's key`, an `alg` fault reported as a key the owner publishes that cannot verify it. `TestValidate_ADelegationRefusalNamesTheClauseItFailed` pins those descriptions, which is what kills the mutants. Do not delete one because mutation says the verdict is unchanged; the fault it names is the point.

**Two checks that look like that pair are not, and deleting them loses a verdict.** The `iat` *presence* check is load-bearing: `jwt.Validate` guards its comparison behind `if iat, present := body["iat"]; present`, so it never requires the claim, while §7.2.1 makes `iat` REQUIRED — removing the check keeps a delegation that carries no `iat` at all. The `kid` header check is the only thing that stops an absent `kid` reaching key selection. An earlier version of this note listed both as cosmetic, which is the kind of sentence that invites the next agent to delete a real check.

A trust mark or delegation header carrying `crit` is refused through `entity_statement.VerifyNoCriticalHeader`, the same check `ValidateStatementHeader` applies to entity statements. This is also a **crash guard**: go-jose v0.10.0 keys a map by each `crit` entry, so `crit: [{}]` panicked before any signature check and `/resolve` answered 500 (#222). Refusing every `crit` is exact rather than strict, because RFC 7515 §4.1.11 forbids an empty list and registered names in it, and requires a recipient to refuse any extension it does not understand, and this library understands none.

The three-part structure check is different: it is a **crash guard**, not a step. A one-segment delegation that decodes to a usable header reaches `parts[1]` and panics, and the trust mark issuer writes that string, so it is reachable from a peer through `/resolve`. Every row of `TestFilterByTrusted_ADelegationThatFailsAStepIsDropped` recovers, so a panic fails the test rather than the package.

`splitDelegation` runs it in two places, and the earlier of the two is the one that matters for the description. `model.TrustMark.UnmarshalJSON` reads `delegation` as `text, _ := delegation.(string)`, so a member present with any non-string value — `null`, a number, an object — arrives as a non-nil pointer to the empty string. Checking the shape only inside the nine steps left that case reaching the ownership branch on a type with no owner, which answered that the trust anchor names no owner for the type: the delegation's own fault reported as the trust anchor's configuration. The guard therefore runs in `verifyDelegationRequirement` before that branch as well. Refusing a non-string `delegation` at parse time is not the alternative — a trust mark parses inside a statement, and failing the parse would take the whole statement down over one mark.

Owner keys are **not** selected through `entity_statement.SelectKey`, which refuses a whole set when any entry lacks a `kid`. §3.1.1 puts the unique-`kid` rule inside the definition of the `jwks` claim only, so a `trust_mark_owners` entry keeps RFC 7517 §4.5's optional `kid` **and may legally carry two keys under one `kid`**. `selectOwnerKeys` therefore returns *every* usable entry carrying the delegation's `kid`, and `verifyDelegation` tries each in turn, because §7.2.2 step 9 says the signature must validate using "one of the Trust Mark Owner's keys identified by" that `kid`. Returning only the first made acceptance depend on array order: an owner mid-rotation publishing old and new under one `kid` had every delegation refused when the new key happened to sit second. A key beside the signing key that this library cannot use — a post-quantum `kty`, no `kid`, a non-string `kid` — is skipped rather than fatal. The `ValidateJWKShape` call inside `selectOwnerKeys` is what decides that for an entry carrying the matching `kid`: without it go-jose's unchecked `kty.(string)` panics, and `TrustMarkOwners` is an exported field, so a deployment can put any shape there.

The owner's signing key goes through `entity_statement.VerifySelectedKey`, so the `use` and modulus rules reach a delegation too: an owner key published with `use: "enc"`, or a 1024-bit RSA key under `RS256`, makes its delegations unverifiable and the marks vanish from resolve responses.

A trust mark and its delegation get the same `model.ClockSkewLeeway` an entity statement does on `iat`, and getting there took an upstream change. On `exp` the allowance governs the **validity verdict** only: a mark whose expiry has passed is still omitted from a resolve response, because §8.3.2 makes the response's `exp` the minimum over the marks it carries and a past minimum makes the whole response unusable to a conforming relying party. Serving one dead mark would cost every other mark in the response, so the mark fails and the endpoint does not. The explicit comparisons in `verifyDelegation` are **not** sufficient on their own: `jwt.Validate` re-checks `iat` and `exp` and runs afterwards, so whatever a caller checks first, go-jose decides the window. It used to compare against `time.Now()` exactly with no way to widen it, which made an earlier version's leeway here do nothing and left the refusal blaming the signature for a clock fault. go-jose v0.10.0 added `JoseOptions.ClockSkewLeeway`, so both `Validate` and `verifyDelegation` pass it and the two layers now agree. If you change the leeway in one place, change it in the `JoseOptions` too, or the stricter of the two wins — and it wins silently only in one direction: when the `JoseOptions` half is the stricter one, the refusal comes from go-jose and this library reports it as a signature failure, because the error is swallowed by the `continue` in the per-key loop. That message is this library's, not go-jose's, which says `exp claim is before current time`. Mutation cannot tell the two layers apart on a verdict alone: they compose with `min`, so either one still enforces the boundary when the other is widened. Only moving both at once changes an outcome, which is what the magnitude tests do. Those tests sit on 60 s and 61 s rather than either side of a gap, so only a 60 s allowance passes; a 59/90 pair leaves 61 to 89 s untested and a 61 s leeway slips through it. Reaching the exact second needs the signing time and the checking time to agree on it, which `withinOneSecond` in `internal/trust_marks/clock_boundary_test.go` arranges: it syncs to the start of a wall-clock second, runs the check, and retries if the second ticks over underneath it. The boundary is therefore deterministic, not flaky, and that includes the delegation `exp` comparison an earlier version of this note claimed could not be tested.

The `len(authorizedIssuers) == 0` guard that used to drop an owned type is gone. It predated delegation validation and would now drop an owned type carrying a valid delegation.

A trust mark goes through the same `VerifySelectedKey`, so the `use` and modulus rules reach it too. `FilterByTrusted` drops a mark it cannot verify and the resolve still returns 200, so an issuer with a legacy key makes its marks vanish silently rather than erroring — document that as a behaviour change, not a refusal.

The read-path checks apply to the **selected** key only — the one the `kid` header names — never to the whole set. That is what keeps a valid but unsupported JWK sitting beside the signing key from taking down the flow: `internal/entity_statement.VerifySelectedKey` runs `alg`, `use` and key strength against that one key, and `internal/entity_statement/key_material_test.go` holds the cases that matter, including a key of a post-quantum `kty` in either position in the set. `go-jose` returns an error rather than panicking on a `kty` it does not know, but its `kty.(string)` assertion would panic on a non-string one, and `model.ValidateJWKShape` is what stands between that and a peer's statement.

## Conventions

- `//todo:` comments mark known incomplete areas across the client, server and model packages (content-type matching, error-type revisits, and handler duplication). They are intentional signposts, not stray notes.
- Logging is optional and nil-safe: `Configuration.LogInfo`/`LogError` no-op when no `*slog.Logger` is set. Use them rather than a package logger, **and never call `cfg.Logger` directly**, because the two helpers are where every logged value is bounded. `model/log_values.go` truncates each string value and key to `MaxLoggedValueBytes` (1 KiB), bounds a group member by member, logs an error by its truncated text, and keeps an `slog.Any` value as it is only when its JSON form fits; otherwise it logs the truncated JSON, or only the value's type if it cannot be marshalled, so a self-referencing value cannot recurse. The helpers check `Logger.Enabled` first, because bounding marshals each `slog.Any`, and "failed to apply policy" logs a peer's whole `metadata` and policy at Info, which a peer could otherwise make the library encode with Info switched off. A value is cut on a UTF-8 character boundary, so a multi-byte character straddling the limit is dropped whole rather than written as U+FFFD. Before this, each call site truncated for itself and five sites missed it (#220): a caller's 8 KB `sub` reached the log whole from `/fetch`, `/resolve` and `/subordinate-status`, and about ninety fields carried identifiers or error text a peer chooses. `server/caller_input_log_bound_test.go` sends a long value with a tail marker to every parameter of every endpoint and is the regression net. Existing `TruncateForResponse` calls inside log arguments are now redundant, and harmless; the response path still needs its own, because `parseError`'s 256-byte bound is separate.
- Tests live alongside code as `_test.go`; `model_test/` and `server_test/` hold shared test helpers/fixtures (e.g. `server_test/testserver.go`).
- A wall-clock assertion must time only the thing it is about. `build(200000)` as an argument to the call being timed put the construction of a 200,000-entry fixture inside the budget, which is what the budget then measured — 1.19s of fixture against a 1s limit, on a loaded machine. Build the fixture first, time the call alone, and keep the budget as a hang detector rather than a measurement: the cap's own semantics belong in a correctness assertion, which is what actually kills a mutant that removes the bound.
- No test in `model` may call `t.Parallel()`. `model/operand_scaling_test.go` reads the package-level `operandWork` counter, which every policy operand comparison increments, so a test running beside it would be counted into its measurement and the assertion would fail intermittently.
- Comments are not to be added by agents. Code is self-documenting and the comments are not welcome
- Commits, if made, must not be co-authored
- When adding a change, tests MUST be written and MUST pass. Data-driven / table-driven tests are much preferred over single-case where possible.
